# PLAN.md

Rules for working in this repo are in `CLAUDE.md`, risks are in `RISKS.md`, and the decision log is `DECISIONS.md`.

**Phases:**
- Phase 1 builds the foundation: data, security, search SQL and quota.
- **Phase 2 ends with a working end-to-end app** (search, chips, shortlists, saved searches, plan, webhook).
- Phase 3 is for security verification, polish, speed and docs.

Each milestone has a **Goal**, the **Files** it touches and an **Acceptance** check. A milestone is done only when its acceptance passes; then commit.

## 1. What the data tells us (measured)

- **Source:** synthetic, generated by `npm run gen:data` (`scripts/gen-dataset.ts`, seeded, so a rerun writes the same bytes).
- **Candidates:** 5,000. No nulls except `experiences[].end_year`, which is null exactly once per candidate (the current job is always `experiences[0]`).
- **Roles:** 13. **Seniority:** junior / mid / senior / staff. There is no lead or principal.
  - **Seniority is a pure function of years:** junior 0–2, mid 3–5, senior 6–9, staff 10–15.
  - `current_title` is the seniority prefix plus the role ("mid" has no prefix).
- **Location:** always US. 10 cities across 9 states (CA = San Francisco + Los Angeles).
- **Skills:** 79, 3–7 per candidate, almost all specific to one role. Traps:
  - "Machine Learning" is a skill held by Data Scientists and some ML Engineers; "machine learning engineers" still means the role.
  - "LLMs" is held only by ML Engineers.
  - "React Native" is not "React".
  - "Go" and "R" are hard to match as text.
  - Python and SQL span several roles.
- **Experience:** 14,344 rows, 1–5 per candidate. There are 30 employers, each with a fixed `company_type` (13 enterprise, 17 startup).
- **Education:** exactly 1 per candidate. 13 schools; degrees BS, BA, MS, MBA, PhD; 14 fields; graduation years 2010–2026.
- **Open to work:** true for 1,256 candidates.
- **Images:** 100 abstract avatar SVGs and 30 logo SVGs in `public/`, generated with the data and served by the app itself.
- **queries.json:** 10 briefs written for this dataset. Their expected ids come from plain predicates in `scripts/gen-dataset.ts`, never from the search SQL. Every stated constraint is AND-ed together:
  - "senior" means senior only.
  - "used to work at X" means a past job at X and not the current one; "currently at a startup" means the current job.
  - "with a security clearance" → `[]`, because one constraint the data can't answer empties the whole answer.
- **Stripe sample:** signed at t=1791820800 (2026-10-12) with the public secret `whsec_rosterly_sample`, so the events are **signed in advance**. It includes a repeat and an out-of-order pair. Expected end state: asterwell free, glenfold paid.
- **With 1 free search, a company must upgrade through the webhook before it can run a second brief.** Webhook robustness therefore also gates search.

## 2. Decisions and assumptions

✅ = confirmed by Om. The rest are assumptions, reviewed when the plan was approved.

| # | Topic | Decision |
|---|---|---|
| A1 ✅ | Model | Claude Haiku 5.5 (`claude-haiku-5-5`, `ANTHROPIC_API_KEY`). Structured JSON output (`messages.parse` + `zodOutputFormat`), thinking disabled, effort `low` |
| A2 ✅ | Webhook signature age | `stripe.webhooks.constructEvent(raw, sig, secret, VERY_LARGE_TOLERANCE)`, so pre-signed events verify. Never pass 0, because stripe-node treats 0 as the 300 s default. Replay safety comes from event-id idempotency plus ordering by `created` |
| A3 ✅ | Chip edits / saved re-runs | Each new result set is a new search and counts on the free plan. Only paging is free |
| A4 ✅ | Vague briefs | Brief interpretation policy (CLAUDE.md § Search rules) plus the mapping table in § 3.4 |
| A5 | Which statuses mean "paid" | Paid ⇔ some subscription of the company has status `active` or `trialing` (trialing is a documented choice). Any other status, or a `.deleted` event, means free |
| A6 | Free allowance | One lifetime counter `searches_used` covering every search. On free, remaining = max(0, 1 − searches_used); on paid it is `null`. A company that searched while paid has 0 left after it cancels ("1 search in total") |
| A7 | Event ordering | Order by `created`, then type precedence (`deleted` 4 > `updated`/other subscription types 3 > paid checkout 2 > `created` 1), then event id. Every delivery order ends in the same state |
| A8 | Loose webhook payloads | Require only `id`, `type`, `created`, `data.object.id` and `data.object.status`. If `metadata.company` is missing, fall back to the stored subscription. A paid subscription checkout (`checkout.session.completed`/`async_payment_succeeded`) activates its subscription; every other non-subscription type (`invoice.*` included) and an unknown company are recorded, ignored, and get 200 (DECISIONS.md). A missing secret returns 500 |
| A9 | Response shapes | Lists return bare arrays. Creates return **200** `{id}`. Add/remove person returns 200 `{ok:true}` and is idempotent. Another company's or an unknown id returns **404** after an explicit lookup. Errors use `{error:{code,message}}`. Candidate field names match candidates.json |
| A10 | Paging | `page` defaults to 1. A non-integer, a value below 1, or one above 10,000 returns 400. Past the end returns 200 with `results: []` |
| A11 | Extra routes | `GET`/`PATCH`/`DELETE /api/shortlists/{id}`, `DELETE /api/saved-briefs/{id}` and `GET /api/me` (the header's company name, added in M9). Chip edits and saved re-runs use `POST /api/search/refine`, so the contract route `POST /api/search` takes exactly `{brief}` |
| A12 | Saved-brief filters | Accept any JSON object up to 16 KB, sanitised. It is validated against the canonical schema only when re-run |
| A13 | `make dev` | Production server: `make setup` builds, `make dev` runs `next start -H 0.0.0.0 -p 3000` and rebuilds if stale. This keeps first-hit compiles from blowing the speed checks. `npm run dev` stays available for hot reload |
| A14 | Input hygiene | `sanitizeText` on all input. A brief that is empty or over 1,000 characters returns 400. Bodies are capped at 32 KB, and non-object JSON returns 400. Checks run in the order 401 → 403 → 400 → 402 |
| A15 | LLM failures | A network error, timeout, 5xx or 429 returns 503 and releases the reservation (the search is not used). An invalid key returns 500 and releases it. A refusal, `max_tokens` stop or unparseable output becomes a zero-result search, which counts |
| A16 | Git | `.env*`, `node_modules` and `.next` are git-ignored. M0 adds `supabase/.temp` and `.qodo/`. `data/` is committed. The branch is renamed to `main` in M0, and `.gitattributes` sets `eol=lf` |
| A17 | Phone access | Browser auth is same-origin: a Next rewrite maps `/supabase/:path*` to local Supabase, so login works from a real phone at `http://<mac-ip>:3000` |

## 3. Design reference

### 3.1 Data model (`supabase/migrations/`)

| Table | Key columns | Indexes / constraints and why |
|---|---|---|
| `companies` | id uuid, slug unique, name | Tenants: asterwell and glenfold |
| `recruiters` | user_id pk → auth.users, company_id → companies | One company per recruiter; RLS: select own row only |
| `candidates` | id text pk, full_name, avatar_url, headline, current_title, current_company, current_company_logo_url, role, seniority (check), years_experience, city, state, country, open_to_work, skills text[] | GIN(skills) for `@>`/`&&`; btree(role, seniority) because most briefs name a role; btree(city), btree(years_experience); partial btree where open_to_work |
| `candidate_experiences` | (candidate_id, position) pk, title, company, company_type (check), company_logo_url, start_year, end_year null, description | (company_type, candidate_id) and (company, candidate_id) serve the "worked at…" EXISTS queries; a partial index `where end_year is null` serves "currently at…" |
| `candidate_education` | (candidate_id, position) pk, school, degree, field, graduation_year | btree(school), btree(degree), btree(field) |
| `shortlists` | id uuid, company_id default `private.current_company_id()`, name check 1–80, created_by, created_at, updated_at; unique(id, company_id) | (company_id, created_at desc) |
| `shortlist_people` | (shortlist_id, candidate_id) pk, company_id, added_by, added_at; FK (shortlist_id, company_id) → shortlists(id, company_id) on delete cascade | The PK makes adds idempotent (`on conflict do nothing`); the composite FK makes cross-company rows impossible |
| `saved_briefs` | id uuid, company_id, brief check 1–1000, filters jsonb check (object, ≤16 KB), created_by, created_at | (company_id, created_at desc) |
| `searches` | id uuid, company_id, recruiter_id, brief, filters jsonb, status pending\|done, total, source brief\|edit\|saved, created_at | (company_id, created_at desc) |
| `search_results` | (search_id, rank) pk, company_id, candidate_id | **Ranked ids are stored at search time, so a page is a PK range scan (well under 300 ms)** |
| `company_usage` | company_id pk, searches_used int ≥ 0 | Its row lock serialises quota takers |
| `subscriptions` | stripe_subscription_id pk, company_id, customer, status, current_period_end null, last_event_id, last_event_created, last_event_type | One row per Stripe subscription; plan = any row active or trialing |
| `processed_stripe_events` | event_id pk, type, created, outcome, received_at | Idempotency |

**Why child tables plus a skills array:**
- Skills are a flat set, so an array with GIN works without joins.
- Experiences and education are records filtered on several attributes *of the same row* (e.g. "currently at a startup"), so they are child tables queried with `EXISTS`.
- At 5k rows the planner may choose sequential scans, and every query runs in well under 20 ms. The indexes match the filter shapes so latency stays flat as data grows. M4 records an EXPLAIN ANALYZE in DECISIONS.md.

### 3.2 Privileges and RLS

- **Baseline migration:** revoke default and existing privileges on tables and functions from `public`, `anon` and `authenticated`.
- **Grants:**
  - `candidates` and child tables: `select` to `authenticated`.
  - `shortlists`: `select`, `insert`, `delete` + `update (name)`.
  - `shortlist_people` and `saved_briefs`: `select`, `insert`, `delete`.
  - `select` only on `searches`, `search_results`, `company_usage`, `subscriptions`, `recruiters` (own row) and `companies` (own company).
  - `processed_stripe_events`: nothing.
- **RLS on every table.** Company-owned tables use `company_id = (select private.current_company_id())` in both `using` and `with check`.
- **`private` schema** (not exposed by PostgREST): `current_company_id()` is SECURITY DEFINER with `search_path = ''` and reads `recruiters` by `auth.uid()`.
- **Function EXECUTE:**
  - `authenticated`: `reserve_search`, `complete_search`, `release_search` (DEFINER) and `get_search_page`, `get_plan` (INVOKER).
  - `service_role`: `apply_stripe_event`.
  - `anon`: nothing.
- **`config.toml`:**
  - Remove `graphql_public` from `[api] schemas`.
  - `enable_signup = false`, anonymous sign-ins off, auth rate limits raised, `jwt_expiry = 86400`.
  - Turn off studio, storage, realtime, edge runtime, analytics, inbucket/mailpit and pooler.
  - Set a unique `project_id`.

### 3.4 Search

**Pipeline** (`lib/server/search/`; `POST /api/search`):
1. `requireRecruiter()`: no or invalid token → 401; not a recruiter → 403.
2. Sanitise and validate the brief → 400.
3. `reserve_search(brief, 'brief')`: one conditional UPDATE on `company_usage`, as SECURITY DEFINER:
   `update company_usage set searches_used = searches_used + 1 where company_id = v_company and (v_paid or searches_used < 1)`
   - It inserts a `pending` search and returns its id.
   - Zero rows → `P0402` → **402 in milliseconds, before any LLM spend**.
   - The row lock plus READ COMMITTED re-check means exactly one concurrent winner.
   - A pending reservation older than 2 minutes is auto-released by the next reserve, so a crash can't eat the search.
4. `parseBrief()`: one Claude Haiku 5.5 call → LLM output schema → canonical `Filters`.
5. `postprocess()`: dedupe and sort, drop true-for-everyone constraints, run the grounding check.
6. `complete_search(search_id, filters)`: only for a pending search of the caller's company. It runs `match_candidates(filters)`, writes `search_results` and marks the search done. Returns `{search_id, total, first 20, searches_remaining}`.
7. On an LLM transport failure: `release_search(search_id)` (pending only) decrements the counter → 503.

`POST /api/search/refine` is the same flow with `source = edit|saved`, and it skips step 4. Direct RPC abuse gains nothing:
- reserve → release nets zero;
- reserve → complete is a normal counted search;
- release after complete is refused.

**Canonical `Filters`** (`lib/shared/filters.ts`, zod; used by the API, UI, saved briefs and SQL). All fields are optional, and enums come from the generated vocabulary:

| Field | Meaning in SQL |
|---|---|
| `roles[]`, `seniority[]` | any of |
| `cities[]`, `states[]` | location matches if the city is in `cities` **or** the state is in `states` |
| `skills_all[]` / `skills_any[]` | `skills @> all` / `skills && any` |
| `open_to_work` | boolean equality |
| `years_min` / `years_max` | inclusive bounds on years_experience |
| `experience[]` of `{company_type?, employers?[], when: any\|current\|past\|never}` | Each condition must hold. `company_type` and `employers` apply to the same experience row. Values of `when`: `current` = current job; `past` = an ended job matches **and** the current job doesn't; `never` = no job matches |
| `schools[]`, `degrees[]`, `fields[]`, `graduated_min` / `graduated_max` | on the education row |
| `exclude{roles, cities, states, skills, schools, degrees, employers}` | none of these |
| `unsupported[]` of `{text, reason, suggestion?: {field, values}}` | any entry → **0 results** |
| `ignored[]` | display only |

`match_candidates(filters jsonb)`:
- **Static SQL** with null-guarded predicates; filter arrays are capped at 50 values.
- **Returns nothing when there is no substantive filter or `unsupported` is non-empty.** This is enforced in SQL as well as in TypeScript.

**LLM call** (`parse-brief.ts`):
- `client.messages.parse({ model: 'claude-haiku-5-5', thinking: { type: 'disabled' }, output_config: { effort: 'low', format: zodOutputFormat(LlmFilters) }, max_tokens: 1000 })`, with request options `{ timeout: 8000, maxRetries: 1 }`. Hedged since M12: if no answer has come after 2 s, an identical second request starts and the first answer wins (DECISIONS.md).
- No sampling parameters: Haiku 5.5 rejects non-default values.
- The system prompt holds the rules, the vocabulary, the mapping table and synthetic few-shots (never queries.json). It is cached with `cache_control` at a 1-hour TTL. Today's date goes after the cache breakpoint.
- The brief is JSON-encoded inside `<brief>…</brief>`, with any `</brief>` neutralised. The prompt says the brief is data, not instructions.
- **`LlmFilters` schema:**
  - Every field is required and non-nullable; empty arrays mean "no constraint".
  - `open_to_work` is `any|yes|no`.
  - Year bounds use sentinels: `years_min` 0 and `years_max` 99 mean none; `graduated_min` 0 and `graduated_max` 9999 mean none.
  - Enums are shared via `$defs`.
  - It is converted to canonical `Filters` in code.
  - **Confirm in M6 that the schema compiles against the live API.**

**Mapping table** (the only vague-word mappings allowed; each row justified with data in DECISIONS.md):

| Words in the brief | Filter |
|---|---|
| experienced, seasoned, veteran | `years_min: 6` (identical to senior ∪ staff; senior starts at 6 years) |
| entry-level, new grad, early-career / mid-level | seniority junior / mid |
| senior+ / at least mid, mid or above | seniority senior + staff / mid + senior + staff |
| over N / N+, at least N, N or more, a bare "N years (of experience)" / under N / at most N, up to N / N–M years | `years_min` N+1 / N / `years_max` N−1 / `years_max` N / inclusive range (a years-vs-seniority contradiction gives an empty result) |
| bachelor's / master's / graduate or advanced degree / doctorate | BS+BA / MS+MBA / MS+MBA+PhD / PhD |
| NYC, Manhattan, Brooklyn / SF, Bay Area / California / Texas / … | New York / San Francisco / state CA (SF+LA) / state TX / … |
| front-end, back-end, full-stack, ML engineer, AE / salespeople, PM, UX/UI designer / designer, marketer, talent acquisition | Frontend Engineer, Backend Engineer, Full Stack Engineer, Machine Learning Engineer, Account Executive, Product Manager, Product Designer, Marketing Manager, Recruiter |
| "engineers", "developers", "devs", "software engineers", "SWEs" alone / "<skill> engineers" | the 7 "… Engineer" roles / the skill + those roles; "machine learning engineers" is always the role |
| K8s, Golang, PostgreSQL, JS, TS, Node, Rails, Vue.js, Tailwind CSS | Kubernetes, Go, Postgres (not SQL), JavaScript, TypeScript, Node.js, Ruby on Rails, Vue, Tailwind |
| ex-X, former X / has worked at X / currently at X | experience `past` / `any` / `current` |
| in the US, US-based, with a degree, currently employed | no filter (true for everyone) |

Rows added in M6 (approved by Om, 2026-10-08): the bare "N years" reading, the synonyms "N or more", "at most N", "up to N" and "mid or above", and the role words back-end, salespeople, designer, marketer, talent acquisition, devs, SWEs and "software engineers". The puffery list also gained motivated, smart, world-class and hungry.

**Suggestions** (the only one-tap fixes, a fixed table in `lib/server/search/unsupported.ts`): principal → seniority staff; SRE / site reliability → DevOps Engineer.

**Model text.** The model writes only reason *codes*, and the sentences a recruiter reads come from a fixed table. `unsupported[].text` and `ignored[]` survive only if they quote the brief (word for word, ignoring case and punctuation), cut to 60 characters. An unsupported entry that doesn't quote the brief keeps its place (so the result stays empty) with the text "Part of the brief".

**Grounding check** (`postprocess.ts`, lexicon in `lib/shared/lexicon.ts`: generated names plus curated aliases):
- Every value in a proper-noun category (cities, states, employers, schools, skills) must match an alias in the brief: whole word, case-insensitive except "Go" and "R".
- A value that doesn't match moves to `unsupported` ("couldn't match X to your brief"). This catches enum-forced guesses such as London → New York.
- **Stated levels are kept:** if the brief names a level (junior, entry-level, new grad, early-career, mid-level, senior, staff) that isn't negated ("not", "no", "non-", "without", or "doesn't/don't need" within the 3 words before it), and the answer has no seniority and doesn't quote that word in `unsupported` or `ignored`, it becomes an unsupported entry, so the result is empty with a reason. The model sometimes "resolved" "junior engineers with 15+ years" by dropping junior (approved by Om, 2026-10-08).
- Cities and states ground each other: an unnamed state added next to one of its named cities is dropped (otherwise "Los Angeles" widens to all of CA), and an unnamed city under a named state is dropped (the state already covers it). "Austin, TX" is just the city.
- Roles, seniority, years, degrees and fields are only logged.
- The eval prints every grounding conversion.

**Ranking.** The set is exact, so the order is for usefulness, stored in `search_results` at search time:
1. The number of `skills_any` matched.
2. Requested skills that appear in the current job's description.
3. An experience condition met by the current job.
4. `open_to_work`.
5. `years_experience` descending.
6. `id` ascending (a stable total order, so every result appears exactly once across pages).

**Untrusted input, end to end:**
- `sanitizeText`, length and body caps.
- `<brief>` delimiting and a schema-constrained, enum-only output, re-validated with zod.
- No SQL is ever built from text.
- The "no substantive filter → 0" guard (TypeScript and SQL) means nothing returns everyone.
- React escapes every string the model echoes back.

### 3.5 Free plan

- `get_plan()` returns `{plan, searches_remaining}`: paid ⇔ an active or trialing subscription; free remaining = max(0, 1 − searches_used).
- Every new result set counts (brief, chip edit, saved re-run); paging never counts.
- A zero-result search (unsupported or vague) also counts. This matters: if it didn't, a burst of vague briefs could all succeed.
- **Pace (every plan):** `reserve_search` also refuses a recruiter's 21st search within a minute or 101st within an hour (`P0429` → 429), counted after the usage row lock, so a burst gets exactly 20. On Free the 402 comes first.
- **Concurrency test:**
  - M5: 50 concurrent `reserve_search` calls with one token → exactly one success.
  - M7: 20 concurrent `POST /api/search` → exactly one 200 and nineteen 402s.

### 3.6 Stripe webhook (`POST /api/billing/events`)

1. `export const runtime = 'nodejs'`. The raw body is `Buffer.from(await req.arrayBuffer())`, never parsed and re-serialised.
2. `Stripe.webhooks.signature.verifyHeader(raw, req.headers['stripe-signature'], STRIPE_WEBHOOK_SECRET, VERY_LARGE_TOLERANCE)`, then our own `JSON.parse`. It makes no network calls. A missing or invalid signature returns 400.
3. Loose parsing (A8). Every `customer.subscription.*` type is applied by its `data.object.status`, and `.deleted` forces `canceled`. A paid subscription checkout means `active`.
4. `apply_stripe_event(...)`, called with the server-only secret key (service_role only), in one transaction:
   - **Idempotency:** `insert into processed_stripe_events … on conflict do nothing`. A duplicate returns early; a concurrent duplicate blocks on the PK.
   - **Ordering:** upsert into `subscriptions` only if (created, precedence, event id) of the incoming event is greater than the stored one, so an older event can never overwrite newer state.
   - If the company can't be resolved, record the event and change nothing.
5. Return 200 `{received: true}` for every validly signed event, including repeats and ignored ones.

**Expected `/api/plan` after each sample event** (a fresh seed starts both companies on free):

| Step | Event | asterwell | glenfold |
|---|---|---|---|
| 1 | asterwell subscribes (created, active) | paid | free |
| 2 | the same event again | paid | free |
| 3 | glenfold newer event (updated, active) | paid | paid |
| 4 | glenfold older event (created, incomplete) | paid | paid (ignored as stale) |
| 5 | asterwell cancels (deleted) | free | paid |

### 3.7 API contract

Every route except billing requires `Authorization: Bearer <Supabase access token>`. Missing or invalid token → 401; a valid user who isn't a recruiter → 403. Errors use `{error:{code,message}}`.

A **card** is `{id, full_name, avatar_url, headline, current_title, current_company, current_company_logo_url, role, seniority, years_experience, location, open_to_work, skills}`.

| Route | Request | Success | Other statuses |
|---|---|---|---|
| `POST /api/search` | `{brief}` | 200 `{search_id, filters, total, results: card[≤20], searches_remaining}` | 400 bad brief · 402 `{error, plan:"free", searches_remaining:0}` · 429 over 20 searches a minute or 100 an hour for this recruiter (`Retry-After: 60`) · 503 model unavailable |
| `POST /api/search/refine` | `{brief, filters, source:"edit"\|"saved"}` | same as above | 400 invalid filters · 402 · 429 |
| `GET /api/search/{search_id}?page=N` | `page` defaults to 1 | 200 `{search_id, brief, filters, page, per_page:20, total, results: card[]}`; never counts | 400 bad page · 404 unknown or other company |
| `GET /api/search/{search_id}/broader` | none | 200 `{options: [{key, total}]}`: for a search that found no one, each one-step relaxation (a chip key, or `unsupported` for all warnings) and how many it finds, most first; `[]` for a search with results; never counts | 404 unknown or other company |
| `GET /api/people/{id}` | none | 200 full candidate (candidates.json shape) | 404 |
| `GET /api/shortlists` | none | 200 `[{id, name, created_at, updated_at, people_count, people: card[]}]` | none |
| `POST /api/shortlists` | `{name}` | 200 `{id}` | 400 |
| `GET` / `PATCH` / `DELETE /api/shortlists/{id}` | PATCH `{name}` | 200 shortlist / `{id, name}` / `{ok:true}` | 400 · 404 |
| `POST /api/shortlists/{id}/people/{person_id}` | none | 200 `{ok:true}`; adding twice changes nothing | 404 list or person |
| `DELETE /api/shortlists/{id}/people/{person_id}` | none | 200 `{ok:true}` (idempotent) | 404 list |
| `GET /api/saved-briefs` | none | 200 `[{id, brief, filters, created_at}]` | none |
| `POST /api/saved-briefs` | `{brief, filters: object}` | 200 `{id}` | 400 |
| `DELETE /api/saved-briefs/{id}` | none | 200 `{ok:true}` | 404 |
| `GET /api/plan` | none | 200 `{plan:"free"\|"paid", searches_remaining: number\|null}` | none |
| `GET /api/me` | none | 200 `{email: string\|null, company: {slug, name}}` | none |
| `POST /api/billing/events` | raw Stripe body + `Stripe-Signature` (no recruiter token) | 200 `{received:true}`, including repeats | 400 bad or missing signature · 500 secret not configured |

### 3.10 Model choice and cost

**Claude Haiku 5.5** (`claude-haiku-5-5`): $0.10 / $0.50 per million input / output tokens for prompts up to 100K. Cache reads cost 0.1× and 1-hour cache writes 2×; the minimum cacheable prefix is 512 tokens. It supports structured JSON output and effort `low` with thinking disabled.

- **Cost per search:** about 4k tokens of system prompt plus schema (cached), about 100 tokens of brief and about 150–250 output tokens.
  - Warm: ≈ 4,000 × $0.01/M + 100 × $0.10/M + 200 × $0.50/M ≈ **$0.00015**.
  - Cold or first write: ≈ **$0.0009**.
  - So **under $0.001 per search**, i.e. more than 1,000 searches per dollar.
- **Latency budget for a new search (target p95 < 2.5 s, against the brief's 3 s):**

  | Step | Time |
  |---|---|
  | Auth | ~10 ms |
  | Reserve | ~5 ms |
  | LLM | ~1.0–1.5 s |
  | Complete (≤5k-row insert) | ~20 ms |
  | Response | ~5 ms |
- **Why not a larger model:** this is closed-vocabulary extraction into enums. Sonnet 5.5 costs about 20× more and is slower, with little to gain. The eval reports accuracy and p50/p95 latency to back the choice.
